# 0004. 決定間隔(action repeat)によるリバランス頻度の構造的制御

## Status

accepted

## Context

時間足の実データ実験(2026-06-11)の診断で、学習済みポリシーは毎バー equity の約1.1倍をリバランスし、評価5ヶ月間でスプレッド+オーバーナイトにより資産の5〜6.6%を失っていた。コストは報酬(log資産変化)に内包されているが、PPO はこの回転を自発的に抑制できていない。毎時間の意思決定は (a) 1決定あたりの期待シグナルがコスト(往復2〜5bp)を下回る、(b) ノイズの多い特徴量に毎バー反応してポジション符号が2〜4バーごとに反転する、という2点で「現実的な取引戦略」から乖離している。

## Decision

trainer に決定間隔 `run.decision_interval`(整数 k ≥ 1、必須キー)を導入する。実装は環境の外側の Gymnasium ラッパー(action repeat)とする:

- エージェントの1決定は連続する k バーにわたり同一のターゲット配分を適用する(各バーで同じ weight を env に転送 = 配分一定保持)
- k バー分の報酬(log資産リターン)を合算して1決定の報酬とし、`info["costs_jpy"]` も k バー分を合算する
- エピソード終端(terminated/truncated)ではインターバル途中でも即座に打ち切る
- 学習環境と評価環境の両方に同一の k を適用する(MDP の一貫性)
- `run.total_timesteps` は従来どおりエージェントの決定数を意味する(消費バー数は約 k 倍になる)

環境リポジトリは変更しない(ADR-0001 の依存方向を維持)。ラッパーは env の公開 API(step/reset)のみを使う。

## Consequences

- ターンオーバー由来のコストが約 1/k になり、1決定あたりの価格変動(√k 倍)対コストの比が改善する
- 決定粒度が粗くなるため、バー内の急変への反応はできない(これは意図した制約)
- k=1 は従来と同一の挙動(既存 config には `decision_interval: 1` を付与)
- 評価指標の `steps` は決定数を数え、Sharpe の年率換算は決定間隔の実時間から自動的に導かれる
