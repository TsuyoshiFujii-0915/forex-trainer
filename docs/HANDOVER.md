## 1. 目的と現在地(サマリ)

**目的**: 現実的な取引戦略(取引しない縮退の禁止)で、コスト控除後に有意なプラスを出す
RL エージェントの構築。目標値はユーザー設定で **walk-forward ネット +7%/年**。

**現在地(2026-07-10)**:

- 最良の**純RLエージェント**(ルール補助なし): `longf ens3` —
  **開発 walk-forward 17フォールド(2009〜2025)でネット +4.7%/年、Sharpe 0.46、
  12/17年勝ち、両時代バケット(2009〜18 / 2019〜25)ともに正**。目標 +7% は未達
- 一時「+7.13%/年 達成」と報告した残差RL構成(ラウンド14)は、ベースルールが
  2019〜2025 への期間適合だったことが判明し**撤回済み**(→ §6 教訓)
- 改善ダイヤル(アーキテクチャ・アルゴリズム・ロールアウト長・アンサンブル規模)は
  +4.7% 付近で飽和。上積みの候補は §8

## 4. 実験プロトコル(必ず守ること)

1. **二時代 walk-forward**: 開発フォールドは評価年 2009〜2025 の17本
   (expanding train、val 直前6ヶ月)。合格には **2009〜18 と 2019〜25 の両バケットで
   ネット正**が必要。configs 例: `configs/wf_r16_long_full/`
2. **封印期間**: 2007〜2008 は最終設計の一発確認専用(使用済み1回)。2026H1以降は
   前向き検証に充てる
3. **RL の前に ceiling 診断**: 新しい特徴量空間/ユニバースでは、まずスクリプト化した
   ルールを env のコストモデルに通してグロスが正であることを確認(グロス≈0の空間では
   何も学べない)。パターンは research/03 と scratchpad の `*_ceiling*.py`
4. **多シード+アンサンブル**: 判定は3シード以上。行動平均アンサンブルは **N=3 が最適**
   (5以上は合意部分しか残らず痩せる)
5. **グロス/ネット分解**: metrics.json の `gross_cumulative_log_return` で
  「シグナル欠如」と「コスト負け」を常に区別する
6. **検証成績を信用しすぎない**: 検証→評価の相関は実測で**負**(−0.3前後)。
   検証はチェックポイント選択のみに使い、構成選択やゲーティングには使わない

## 6. 確定した知見と教訓

**効いたもの**:
- ロールアウト長 n_steps 256→**1024** + 300k steps(最大の単一改善: −1.1→+4.7%/年)
- クロスセクショナル特徴量(`xz_mom24`/`xr_mom24` — フラットMLPはペア間ランキングを
  自力推論できない)
- 3シード行動平均アンサンブル(共有シグナルがある場合のみ有効)
- 符号付き資金調達(旧・対称オーバーナイト課金は戦略を年約2.7%過小評価していた)

**効かなかったもの(再挑戦時は要注意)**:
- ペア間attention(xattention)、RecurrentPPO、TQC(無取引に縮退)、正則化PPO
- 決定間隔 k>1 は RL には有害(ルールには有効)
- ハードなレバレッジ上限、自己ボラ・ターゲティング、ドローダウン制御オーバーレイ
  (リターンを増やさない。損失はボラ・クラスタでなくレジーム転換で発生するため)
- 検証ベースのシード/フォールド選別(相関が負)

**最大の教訓(撤回事件)**:
- 同じ検証フォールドに設計反復を重ねると、コードが正しくても**研究プロセス自体が
  in-sample 選択**になる。ルール(リバーサル)の方向自体が発見窓の産物だった。
  対策が二時代基準と封印期間
- **価格データは必ずスパイク監査**: yfinance 旧データに「±数百%→翌日全戻し」の不良
  プリント(NOKJPY ±460%等)。リバーサル系は不良ティックを偽の利益として刈り取る。
  修復ロジックは scratchpad 参照、修復済みキャッシュを使うこと

## 7. 運用上の落とし穴

- **Dukascopy datafeed は激しくスロットリング**(数時間〜日単位の IP ブロック実績)。
  `forex-fetch-dukascopy` はリクエスト間隔・リトライ実装済みだが、並列取得は厳禁
- **学習バッチ実行中にソースを編集しない**(editable install のため実行中バッチが
  不整合なコードを import して落ちる。実際に11 run 損失した)
- 日足評価は **warmup(32)+窓(31)で評価区間の先頭63バーが消える**(半年指定なら
  実質1四半期)。フォールド間では一貫しているので比較は有効
- `normalize: true`(観測窓内z-score)は低速特徴量とペア間水準比較を破壊する。
  クロスセクション課題では `false` + スケールの揃った特徴量を使う(residual 使用時は
  config が強制)

## 8. 推奨する次の一手(優先順)

1. **テール損失の抑制**: longf の負け年(2009/2015/2019: −15〜33%)はレジーム断絶年。
   報酬はいじらず観測側で(レジーム条件付き特徴量: クロスセクション分散、実現相関、
   ドローダウン状態など)。改善すれば Sharpe 0.46→0.6+ が視野
2. **時間足 signed ユニバース**: 時間足キャッシュ(2015+)に carry を付与して
   longf 系を再検証(学習密度24倍。ただし R11 の失敗経緯を踏まえ観測設計に注意)
3. **前向き検証の定常運用**: 四半期ごとに新データで longf ens3 を追試し、
   証拠を蓄積する(封印期間はもう使えない)
4. サイズアップは Sharpe が上がるまで**非推奨**(−30%級の年が拡大し margin call
  (閾値0.2)に近づく)

## 9. 再現手順(最良エージェント)

```bash
# データ(手元に無い場合): yfinance 9ペア日足 → スパイク修復 → キャリー付与
# (修復スクリプトは scratchpad にあったもの — 必要なら research/04 の記述から再構成)
uv run forex-add-carry --input data/jpy_9pairs_1d_2003_clean.parquet \
  --output data/jpy_9pairs_1d_2003_carry.parquet --lag-days 60

# 1フォールドの学習×3シード → アンサンブル評価
for s in 1 2 3; do
  uv run forex-train --config configs/wf_r16_long_full/wf2024_r16_longf.yaml --seed $s
  uv run forex-eval --run runs/wf2024_r16_longf/<timestamp>
done
uv run forex-ensemble-eval --runs runs/wf2024_r16_longf/* --runs-root runs
```

全17フォールドのバッチ実行例・集計スクリプトの形は research ログ各所のとおり
(実行→評価→ens3→時代バケット集計)。
